# Чайный город — MVP ИИ-консультанта. Памятка для разработчика

Этот документ — краткая передача проекта. Что сделано, как устроено, что проверить перед боевым запуском и какая проблема осталась открытой.

## 1. Что это

Веб-чат с ИИ-консультантом по чаю. Три слоя, как и просили в ТЗ:

1. **Веб-морда** (`public/index.html`, `public/css/style.css`, `public/js/chat.js`) — чат в браузере, история диалога привязана к cookie `tea_cid` (только ID разговора, 30 дней).
2. **Бэкенд-приёмник** — часть `public/api/chat.php`: валидация запроса, лимит частоты запросов, определение/генерация `conversation_id`.
3. **Бэкенд-ответчик** — вторая часть `public/api/chat.php` + `src/OpenAiClient.php`: сборка запроса к OpenAI Responses API, разбор структурированного ответа, сохранение истории, логирование.

База данных не используется. История диалога хранится в JSON-файлах на диске (`storage/conversations/`), по одному файлу на `conversation_id`. Cookie в браузере хранит только сам ID — сообщения на клиенте не хранятся (кроме кэша отрисовки в sessionStorage, чтобы не мигал экран при перезагрузке страницы).

## 2. Структура проекта

```
public/            ← DocumentRoot на проде (Apache/Nginx смотрит СЮДА, а не в корень)
  index.html, css/, js/chat.js
  api/chat.php      ← единая точка входа API
data/teas.json      ← каталог чая (редактируется без правки кода)
prompts/tea-master.txt ← системная инструкция консультанта (редактируется без правки кода)
src/                ← классы бэкенда (Config, Catalog, PromptLoader, HistoryStore, RateLimiter, Logger, OpenAiClient)
storage/            ← runtime-данные: conversations/ (история), ratelimit/ (счётчики)
logs/requests.log   ← JSON Lines лог каждого запроса
tests/smoke_test.php ← офлайн-тест без обращения к сети/OpenAI
preview/index.html  ← автономный HTML-макет БЕЗ PHP и БЕЗ реального ИИ (для быстрой демонстрации UI/UX, ответы — по ключевым словам)
.env.example        ← шаблон конфигурации, скопировать в .env и заполнить
README.md           ← более подробная документация (структура, деплой, безопасность)
```

## 3. Как запустить локально

Зависимостей (composer/npm) нет — чистый PHP 8.2+.

```bash
cp .env.example .env
# открыть .env и вписать реальный OPENAI_API_KEY
php -S 127.0.0.1:8091 -t public
```

Открыть `http://127.0.0.1:8091/`.

На проде: DocumentRoot указывает на `public/`, остальные папки (`src`, `data`, `prompts`, `storage`, `logs`) физически лежат ВЫШЕ веб-корня или закрыты через `.htaccess`/конфиг сервера (я положил `deny from all` в `.htaccess` в каждой такой папке как доп. слой защиты — но полагаться нужно в первую очередь на правильный DocumentRoot).

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `OPENAI_API_KEY` | ключ OpenAI | — обязателен |

**Важно про модели**: названия `gpt-5.6-terra` / `gpt-5.6-luna` были даны в исходном ТЗ пользователем. У меня нет возможности свериться с актуальной документацией OpenAI на предмет того, существуют ли они в точности под такими идентификаторами и доступны ли конкретному ключу/проекту — это нужно проверить самим при первом реальном вызове (сразу будет видно по ошибке API, если имя модели неверное).

## 6. Уже найденный и исправленный баг

При первом реальном тесте на локальной машине (PHP 8.5, встроенный сервер `php -S`) браузер показывал «Сервер вернул некорректный ответ». Причина: `curl_close($ch)` — начиная с PHP 8.0 это no-op, а в PHP 8.5 вызов помечен deprecated, и notice об этом печатался прямо в тело HTTP-ответа (потому что у встроенного сервера по умолчанию `display_errors=On`), ломая JSON на фронтенде.

Исправлено в текущей версии:
- убран вызов `curl_close()` в `src/OpenAiClient.php` (просто не нужен);
- в `public/api/chat.php` добавлены `ini_set('display_errors', '0')` + `ob_start()`/`ob_end_clean()` перед отправкой JSON — защита от любого постороннего вывода в будущем, кто бы его ни вызвал.

## 7. ОТКРЫТАЯ ПРОБЛЕМА — нужно решить разработчику

После применения фикса выше на локальной машине пользователя (Mac, `php -S 127.0.0.1:8091`) браузер по-прежнему показывал ту же ошибку. Диагностика зашла в тупик на следующем шаге: прямой

```bash
curl -s -X POST http://127.0.0.1:8091/api/chat.php \
  -H "Content-Type: application/json" \
  -d '{"conversation_id":null,"message":"тест"}'
```

вернул **не JSON и вообще не ответ от локального PHP-сервера**, а полностью посторонний HTML — страницу claude.com «App unavailable in region». Это значит, что запрос до `127.0.0.1:8091` физически не дошёл — что-то на машине пользователя перехватывает/переадресует трафик до localhost (свежий процесс `php -S` при этом честно писал в свой собственный лог `[200]` на другие запросы, так что сервер жив, просто конкретно этот curl до него не долетел).

Вероятные причины (по убыванию вероятности):
- системный HTTP(S)-прокси или VPN-клиент (корпоративный агент безопасности, Zscaler, Cloudflare WARP и т.п.), который заворачивает весь трафик, включая localhost;
- переопределение `127.0.0.1`/`localhost` в `/etc/hosts` или локальном DNS-фильтре;
- alias/wrapper на `curl` в шелле;
- curl запускался не в том терминале/сессии, где реально поднят `php -S` (два процесса на одном порту, либо процесс уже не жив).

Чек-лист для разработчика, чтобы добить это на месте:

```bash
env | grep -i proxy                              # прокси-переменные окружения
cat /etc/hosts | grep -v '^#'                     # подмена localhost
type curl                                         # curl не алиасован
lsof -nP -iTCP:8091 -sTCP:LISTEN                  # кто реально слушает порт
curl -v http://127.0.0.1:8091/                    # обычный GET index.html — работает ли порт вообще
```

Пока эта проблема жива, живой сквозной тест (браузер → чат.js → chat.php → OpenAI) не подтверждён — офлайн-часть (без сети) полностью рабочая и протестирована.
